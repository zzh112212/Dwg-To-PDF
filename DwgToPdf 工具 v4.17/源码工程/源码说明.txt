【工程概况】
    - 工程文件：DwgToPdf.csproj（SDK 风格，WinForms 桌面应用）
    - 目标框架：.NET Framework 4.8（net48）
    - 输出类型：WinExe（GUI 程序），生成 DwgToPdf.exe
    - 程序集版本：4.17.0.0（csproj 中 Version/FileVersion/AssemblyVersion 三处一致）
    - 界面版本号：Program.Version = "v4.17"（主窗口标题栏显示）
    - 与 AutoCAD 交互：COM 后期绑定（Late.cs，无需类型库）+ accoreconsole 脚本（.scr/.lsp）
    - 本工程不引用任何第三方 NuGet 包 / 本地 DLL
    - JSON：FrameCache / FrameTemplateLibrary 用内置 DataContractJsonSerializer；
      AppSettings（settings.json）为手写 JSON 序列化/解析（.NET 4.8 无 System.Text.Json）
    - 额外发布文件：extframe.lsp、extframe_company.lsp（图框识别 LISP 脚本，
      GB2312 编码，随构建拷贝到输出目录）、公司图框标准库.json（公司版图框特征库）
    - 源文件规模：29 个 .cs + 2 个 .lsp + 1 个 .json（v4.3 新增
      AppSettings.cs / PdfContentCheck.cs / SettingsForm.cs；
      v4.4 新增 ConvertReport.cs，v4.5 起仅作日志失败分类摘要用途）

【如何编译】
    方式一（命令行，需装有 .NET SDK）：
        dotnet build "源码工程\DwgToPdf.csproj" -c Release
        # 产物：源码工程\bin\Release\net48\DwgToPdf.exe、DwgToPdf.exe.config、
        #       extframe.lsp、extframe_company.lsp、公司图框标准库.json
    方式二（Visual Studio）：
        直接打开 DwgToPdf.csproj → 生成解决方案（Release）。
    编译成功后，把 bin\Release\net48\ 下的 DwgToPdf.exe、DwgToPdf.exe.config、
    extframe.lsp、extframe_company.lsp、公司图框标准库.json 复制到 发布程序 v4.8\
    覆盖即可完成发布。
    注：v4.5.1 起新增 App.config（高 DPI PerMonitorV2 声明），SDK 工程自动
    生成到输出目录 DwgToPdf.exe.config，随发布一并复制（不可省略，否则高分屏
    125%/150% 缩放下界面发糊）。

    说明：bin\ 与 obj\ 是编译产生的临时目录，不属于源码。
    注意：SelfTest 自测试工程的 bin\Release\net48\ 下可能缺少 .lsp/.json 文件
    （csproj 的 CopyToOutputDirectory 偶发不生效），需手动从源码工程复制。

【三阶段管线架构（v4.3 现状）】
    阶段1 图框识别（accoreconsole + extframe.lsp，FrameCache 命中可跳过）
        识别链：公司版（extframe_company.lsp，只扫公司图框层）→ 通用版补识别
        （extframe.lsp）→ 仍失败才 COM 兜底。每文件一个 accoreconsole 会话，
        LISP 用 DXF 组码遍历 Model 空间求图框 → 写 out.txt → 结果合并写入
        <输出文件夹>\frame_cache.json（FrameCache）。
        · v3.8.1：LISP 内容内联到 .scr（ReadLspContent 缓存），规避 accoreconsole
          2021 load 失败问题；同时去掉 /isolate 参数。
        · v4.17：改回 (load) 外部加载（LISP 先复制到临时 ASCII 目录，脚本写
          (load "正斜杠路径")），实测快 419ms/张（约 10.5%）；若 (load) 取不到
          结果自动内联重试一次兜底。v3.8.1 的"(load) 必失败"结论已证伪——
          真因是路径中的反斜杠，改正斜杠后 (load) 完全可用。
        · v4.2（extframe.lsp 升级，仅 LSP 改动）：
          ① ent-pts 增加 LINE 分支（读组码 10/11 端点）
          ② pts->box 由 (= (length p) 2) 改 (>= (length p) 2)，接受 3D 点自动降 2D
          ③ v42-score：短边命中 A 系标准图框尺寸（210/297/420/594/841/1189/
             1682/2378 ±25mm）加 10000 分；短边 < 100mm 淘汰；否则按面积。
             解决 H47/H77 由 4 条散 LINE 围成图框的图纸识别异常。
        · v4.3（块图框识别，UI "识别块图框"勾选时启用）：
          extframe 增加 blockMode / extraBlocks 两个参数；block-box 展开 INSERT
          块定义（tblobjname + entnext 遍历），收集块内闭合 LWPOLYLINE bbox
          （特征判定：短边 >= 50mm 才视为图框块）；块名命中 extraBlocks 列表
          则强制视为图框。开启会拖慢识别（默认关闭，由用户勾选）。
        · v4.3（图框合理性校验 FrameValidator，FrameExtractor.cs 内静态类）：
          识别结果不可信直接判失败（原因="图框问题"），不硬出裁切 PDF。
          company/legacy（公司图框层）/ BLOCK:*（块识别命中）→ 放行；
          auto（通用版按层 bbox）需同时满足：
            比例（长/短）≤ 3.0、短边 100~1600mm、长边 ≤ 2500mm
          否则 IsAcceptable 返回 false → 该文件不写 FrameCache（防下次缓存
          命中又错）、ConverterEngine._frameRejectedPaths 记录后跳过阶段2/3，
          UI 直接从待处理栏移到失败栏。
        · 早期收割：轮询 .out 文件，写出且大小稳定 3s 即 Kill 进程并采纳结果，
          180s 超时仅作最后防线（防代理实体图纸"完成识别后退出挂起"）。
        · 识别并发：SmartConcurrency.RecognitionMax = 12（v4.0 实测最优，
          v4.1 起硬编码 UI 不可调；另 min(CPU, max) 保护）。
        · v4.4（FrameCache 内存快照）：RunCore 开始一次性把 frame_cache.json
          加载到内存（FrameCache.Snapshot），阶段1 命中统计与阶段3 出图查询
          均走内存（FrameCache.TryGetFrom，键=路径+大小+修改时间与旧逻辑
          完全一致）；阶段1 识别结果落盘后刷新一次快照（纳入本轮新识别图框）。
          消除旧版"每文件各读一次 JSON"的重复磁盘 IO，行为与 v4.3 等价。
        · v4.12 修订（2026-09-13，识别完整性修正）：
          extframe.lsp 在输出主结果前始终写一行 EXTENT|x0 y0 x1 y1
          （zoom-e 范围 = 图纸真实全图范围）；当 auto/legacy 结果没覆盖全图范围
          （v49-clean 不通过）时，仅在同时满足三闸门才改用全图范围当图框
          （来源标记 EXTENT）：
            ① v49-plausible：全图范围本身是合理幅面
              （短边 100~2100、比例 ≤3、长边 ≤3000；短边>1600 另需 √2±10%）；
            ② v49-block-covers：bseen 中存在与全图范围基本重合的块
              （容差 max(25mm,3%)）——"整幅图框就是一个块"（H47 EQWE 即此）；
            ③ v49-fit4a0：全图范围能被最大纸型 4A0 容纳（长边 ≤2368 / 短边 ≤1672），
              否则会触发 PageSpec 的"超大图框兜底取最小纸"→ 整张被压成 A4。
          不满足三闸门 → 保持原识别框 + 输出 WARN|extent-out；
          修正时额外输出 CANDIDATE|…（修正前的候选框）。
          C# 侧（FrameExtractor）：FrameBox 增加 Extent / ExtentOut；
          ParseResult 解析 EXTENT| / WARN| / CANDIDATE|（辅助行不参与主结果解析）；
          FrameValidator 放行 EXTENT 并按同口径复核（ExtentMaxLongEdge/ShortEdge）。
          ConverterEngine 在阶段1 校验循环写两类日志（"已按全图范围出图…" /
          "图框外检测到其他内容…"）。
          回归：183 张（H56E 40 / 557 34 / PISCES 17 / 测试文件二 24 / 失败文件 11 /
          H77 38 / H47 19）中仅 4 张变化，均为"由被裁改为完整"。
          注意：v49-fit4a0 与 C# 的 ExtentMaxLongEdge/ShortEdge 是同一口径的硬约束，
          改纸型表（PageSpec）时必须同步复核，否则会出现"按全图范围出图但被压成 A4"。
        · v4.14（2026-09-13，A3 识别扫描优化，仅 LSP 改动，零回归）：
          目标：降低阶段1 识别成本（识别约占全量总耗时 28%）。
          测量（探针 _探针\p_census.lsp / p_types.lsp，MILLISECS 计时）：
          识别 LISP 成本 ≈ 实体数 × ~33µs；热点 = 49777 条 LINE 被 ent-pts 与
          v49-scan 各解析一遍 + 5.9 万个 ELLIPSE/ARC/POLYLINE 实体只为"点集 gbox"
          干活（而 gbox 实际总被 zoom-e 的 EXTMIN/EXTMAX 覆盖）。
          三项改动（均可证明等价，ef.txt 逐字节 = 基线）：
            ① 单遍化：主循环 cond 内联 LINE/LWPOLYLINE——图层盒与扫描共用一次 DXF
              解析；ent-pts 删除；其余类型不再做无用的 assoc-8/ent-pts。
              v49-scan 签名改 (d ent t0)（t0 由调用方传入，省一次 assoc 0）。
              CIRCLE/ARC 提到 cond 最前：不再重复走 10-14 组码（圆心必在半径盒内，
              gbox 结果不变）。
            ② 标量化 gbox：曾用 4 个标量替代 add-pt 的逐点列表分配 → 实测无收益
              （AutoLISP 函数调用开销抵消），放弃，保留 add-pt。
            ③ 兜底延迟（决定性）：点集 gbox 只在 zoom-e 失效时才有用（EXTMIN/EXTMAX
              退化，如全部实体在冻结/关闭层）——把 gbox 累积从热循环整个移除；
              zoom-e 失效时由 v49-gbox-rescan 按 pre-A3 语义补扫
              （v49-gb-scan / v49-gb-poly 复刻旧逻辑）。
          效果（逐文件 MILLISECS）：FAILSET 3531→1234ms(-65%)、PISCES 609→266ms(-56%)、
          H77 203→110ms(-46%)。全量墙钟（6 轮交错 A/B，出图 3s 超时截断）：
          中位 515.4s → 470.8s（-8.7%）。
          等价性：全量 184 张双版本 cache dump 逐条一致（通用版 181 + 公司版 40）。
          注意：extframe.lsp 必须保持 GB2312 编码（本次同时修正了此前被写成 UTF-8
          的隐患）；主循环 box/hlines/vlines/prects 语义未变，改动只在 gbox 计算时机。
          新增函数：v49-gb-poly / v49-gb-scan / v49-gbox-rescan。
        · v4.15（2026-09-15，含图片图纸高清出图；详见手册第26章）：
          需求：用户提出"含图片图纸需要调光栅图像质量（建议 1200/4800dpi），做成设置入口"
          （附打印对话框「PDF 选项 → 质量」截图与样图）。
          关键实测：accoreconsole 的 **-EXPORT 不认打印质量/设备**（改设备名/改 pc3/改
          DefaultConfig 输出均逐字节相同，图片被压到 ~26-44dpi；出图日志显示实际用默认设备）；
          而 **COM（打印）路径认 pc3 的"光栅图像质量"**（2400/600 → 图片 ≈40dpi；
          2400/2400 或 4800/4800 → ≈161dpi，且两者像素完全相同）。
          实现：
            · extframe.lsp / extframe_company.lsp：输出 `IMG|n` —— IMAGE 实体 +
              **图片型** OLE2FRAME（组码 3 含 "Picture"）+ *UNDERLAY 数量（零遍历成本；
              只认图片型 OLE，避免普通 OLE 图纸大面积改变输出——首次实现即踩此坑）；
            · FrameExtractor：FrameBox.ImageCount + 解析 IMG| 辅助行；
            · FrameCache：Entry 新增 [DataMember "img"]，**Version 4 → 5**；
            · RasterPlotterFactory（新增）：以用户 HQ pc3 为模板生成
              `DwgToPdf_Quality<dpi>.pc3`（改 Raster_Limit/Monochrome_Raster_Limit；
              dpi>2400 时同步抬矢量质量，满足"光栅 ≤ 矢量"）。容器格式：
              首行 + 前缀(b"pmzlibcodec"+4B magic) + LE32(解压长) + LE32(压缩长) + zlib 流，
              **长度字段必须重算**，否则 AutoCAD 静默忽略整个 pc3；
            · PrintQuality/PrintOptions/AppSettings/SettingsForm：新增
              「含图片图纸的高清出图」（关闭/1200/2400 默认/4800）；
            · ConverterEngine.Plot：含图片图纸跳过 accore、直接走 COM + 该 pc3
              （失败自动回退 accore 路径）；阶段1 日志列出这类图纸；
            · CadConverter：`Convert(..., knownLl, knownUr)` 支持传入识别缓存里的图框范围，
              **跳过 TryGetFrameExtents 的逐实体 COM 遍历**（10 万实体 ≈390 秒！单张 555s → 47.5s）。
          验证：样图图片 489×315 → 2930×1886（≈161dpi）；H47 13 张无图片图纸逐字节不变、
          6 张含图片的图片像素翻倍（80dpi → 160dpi）。
        · v4.15 修订（2026-09-16，全量 183 张实测后的两项重大修正；详见手册第26章末）：

            · 诊断开关（默认关闭）：DWGTOPDF_COM_NOEXT / DWGTOPDF_COM_PLOTTER /
              DWGTOPDF_KEEP_BLANK（保留空白 PDF 供解剖）。
          【修复后全量】744.1s（基线 725.3s，+2.6% 噪声内）；成功 181/181，失败=图框问题 2；
            COM 回退重试 0 次；走 COM 高清仅 2 张（L42P_DL9H5056/DL9H5059）；

    阶段2 预处理（COM 多实例，仅图纸副本）
        PageSetupPreprocessor：每 worker 独立 AutoCAD 实例 + 动态任务池
        （PrepMax = 4；COM 启动错开 800ms，防多实例同时抢锁），
        设置副本 Model 布局页面设置。有边距（非贴边）时精确模式：
        · 窗口 = frame±M（M=10mm）SetWindowToPlot
        · 固定比例 SetCustomScale(s, 1)（s 分母=窗口=frame+2M，方案 G）
        · v4.3 显式清零 PlotOrigin=(0,0)（先设）→ CenterPlot=true（后设）：
          批量 dwg 常已存 PlotOrigin 偏移（用户前置设置/模板继承），-EXPORT W
          继承源图 PageSetup 导致内容偏移纸面非中心。实测 PlotOrigin=(0,0)
          与 CenterPlot 可共存（v3.8 注释"不能设 PlotOrigin"在批量场景不成立，
          顺序必须 PlotOrigin 在前 CenterPlot 在后，保证后者生效）。
        · 打印设备：恒为 DWG TO PDF.pc3。v4.16 起 HQ pc3 退役（负优化，手册第28章）；
          v4.17 修订十五删除 HighQualityThresholdBytes 阈值传递链，设备名一律取
          PrintQuality.StandardPlotterName，媒体名直接取 PageSpec 的 Media。
        · v3.9：预处理进度上报带 RunPhase.PageSetup 阶段信号。

    阶段3 批量出图（accoreconsole -EXPORT，失败→COM 兜底）
        PlotSession：生成 -EXPORT 脚本（W 窗口=frame±M）→ 出 PDF → 移动到
        <输出文件夹>\PDF文件\<相对子目录>\（v3.9.1 保留输入目录层级，同名 (2)(3)）。
        · 空白/异常 PDF 拦截（v4.3 质量审查多元化 PdfContentCheck；v4.17 加严为 5 维）：
          出图后 5 维综合检查，任一不达标即判失败（记录 reason 区分原因）：
            ① 文件大小 < 阈值（默认取 settings QualityMinFileSizeBytes=10KB；
               若 <=0 回退纸型估算：每平方米 ≥ 1KB、最少 2KB）
            ② PDF MediaBox 与期望纸型偏差 > 5mm → "页尺寸异常"
               （v4.17：长边、短边**都**校验；无 MediaBox 直接判失败）
            ③ /Contents 累计流字节数 < minContent（每平方米 1KB 最少 2KB）
               → "PDF 内容流过空"（v4.17：修 contentLen==0 漏判——除非存在
               大流 >5MB 的例外，否则 0 字节一律判失败）
            ④ 页数 > 1 → "页数异常"
            ⑤ 缺 %%EOF 结束标记 → "PDF 结构不完整"（v4.17 新增，识别截断 PDF；
               读异常时保守放行，避免误杀）
          判失败后走 COM 兜底重出一次，仍不达标才标记失败。
        · 打印设备：恒为 DWG To PDF.pc3（PrintQuality.StandardPlotterName）。
          v4.16 起 HQ pc3 退役（负优化，见手册第28章）；v4.17 修订十五删除
          IsHighQuality/PlotterFor/MapMedia 与 HighQualityThresholdBytes 传递链。
    兜底：任一阶段失败 → FallbackCom，限流 FallbackMax=4（SemaphoreSlim），

【关键实测结论（改代码前必读）】
    1. -PLOT 在 accoreconsole 下不产出 PDF → 出图用 -EXPORT PDF。
    2. -EXPORT 无法会话内控制纸张（恒为图纸默认页面设置）→ 用预处理副本方案。
    3. accoreconsole 不支持 ActiveX → LISP 用纯 DXF。
    4. 脚本编码必须 GB2312（.scr/.lsp/.out 一致），系统 ACP=936 时。
    5. 设 CanonicalMediaName 前必须先设 ConfigName="DWG To PDF.pc3"（否则"输入无效"）。
    6. 缓存必须从输出文件夹读（FrameCache.TryGet 双参重载）。
    7. Layout COM 对象无 CustomScale 属性（抛 DISP_E_UNKNOWNNAME），
       正确 API 是 SetCustomScale(分子, 分母) 方法（v3.8 反射探针验证）。
    8. PlotOrigin 与 CenterPlot 的关系（v3.8 与 v4.3 结论不同，注意场景）：
       · v3.8 单实例场景观察：显式设 PlotOrigin=(0,0) 会禁用 CenterPlot，
         内容贴左下角 → 当时删掉 PlotOrigin 设置。
       · v4.3 批量场景实测：dwg 已存 PlotOrigin 偏移（用户前置设置/模板继承）
         时，-EXPORT W 继承源图 PageSetup → 内容偏移纸面非中心，仅 CenterPlot
         不够。修复：显式设 PlotOrigin=(0,0) 再设 CenterPlot=true，两者可共存
         （顺序必须先 PlotOrigin 后 CenterPlot）。**修复必须实测批量场景**，
         不要被早期注释"不能设 PlotOrigin"一刀切限制。
    9. 精确模式（SetCustomScale + CenterPlot + PlotOrigin=(0,0)）才能均匀居中。
    10. 识别 frame ≠ 真实图框外框（识别容差）→ 出图窗口必须 frame±M 外扩，
        否则图框显示不完全（v3.8 方案 G 经验）。
    11. accoreconsole 2021 的 (load) 命令**可用**，v3.8.1 的"必失败"结论已证伪
        （v4.17 实测）：真因是脚本里写的 Windows 反斜杠路径；改为正斜杠路径后
        (load) 正常加载外部 .lsp，且比内联整段 LISP 快 419ms/张（约 10.5%，
        省去 .scr 传输/解析开销）。v4.17 恢复 (load) 加载，并保留"取不到结果
        则内联重试一次"的兜底。注意：LISP 文件须先复制到纯 ASCII 临时目录，
        脚本路径用正斜杠。
    12. accoreconsole 2021 的 /isolate 参数不可用（报 "Copying folder failed errno=3 /
        Failed to create registry keys"，即使纯英文路径）→ 必须去掉 /isolate（v3.8.1 验证）。
    13. accoreconsole 2021 的 /i 参数支持中文路径（DWG 文件路径含中文可正常打开），
        但 /isolate 的 userDataFolder 不支持中文路径（v3.8.1 验证）。
    14. AutoCAD 2026 无上述 /isolate 问题；v3.8.1 的"去 isolate + 系统 Temp"
        修复在 2026 下同样兼容。关于 (load)：2026 与 2021 在正斜杠路径下均可正常
        加载（v4.17 复核），两版本行为一致。
    15. accoreconsole 加载的 AutoLISP 不一定有 VL 函数（strcasecmp /
        vl-string-search 实测不可用）→ 比较用内置 =（大小写不敏感场景）或手写
        substr 实现（v4.3 块识别 name-in-extras 即手写实现）。
    16. 图框由 4 条独立 LINE 围成（非 polyline 非块）的图纸：extframe.lsp 必须
        处理 LINE（组码 10/11）；AutoLISP 3D 点 (x y z) 长度为 3，判断要用
        (>= (length p) 2) 并取前两维，否则 LINE 端点被丢弃（v4.2 修复）。
    17. 通用版按 layer bbox 合并会把同层散 LINE 撑成异常大框（H47 风扇
        5534×841 等）→ 别硬出，FrameValidator 阈值（比例≤3 / 短边 100~1600 /
        长边≤2500）拦截判失败（原因="图框问题"），人工在 CAD 处理（v4.3）。
    18. TableLayoutPanel 动态加列陷阱：ColumnCount=N 时把控件 Add 到 index>=N
        会被静默丢弃（不报错、不显示）——"设置…"按钮消失即此因。加列必须
        同步改 ColumnCount（v4.3 修复 buttonsRow 4→5）。
    19. progress.Report 状态变更为 Failed 时不能再带 Booting=true：
        MainForm.ApplyUpdate 见 Booting=true 早 return 跳过 UpdateRow，
        UI 失败行停在待处理栏不移（v4.3 修复）。规则：状态变更不发 Booting。
    20. 质量审查只查文件大小会漏判"大小达标但内容全空"的伪 PDF（accoreconsole
        静默产空白 PDF）→ PdfContentCheck 4 维（大小/MediaBox/内容流/页数），
        手写 PDF ASCII 解析无库依赖（v4.3）。**v4.17 加严为 5 维**：补 %%EOF
        结束标记检测（识别截断 PDF），并修复"内容流 0 字节""MediaBox 短边不符"
        两类漏判（详见变更摘要）。
    21. .NET Framework 4.8 无 System.Text.Json → AppSettings 手写 JSON
        序列化/解析（v4.3）。
    22. FrameCache 快照必须在"阶段1 识别结果落盘后"刷新一次（v4.4）：
        本轮新识别的图框只写入了磁盘 JSON，阶段3 出图查询若还用旧快照
        会全部落空走不出图。刷新点在阶段1→阶段2 之间。
    23. 转换报告登记语义（v4.4）：AddRecord 同一文件重复登记时覆盖
        （重试/兜底轮取最终态）；停止时未登记过终态的文件补"已停止"，
        已登记的不覆盖（保留真实结果）；报告在 RunCore finally 写，
        停止/异常也要能出报告。新增失败原因文案必须同步
        ConvertReport.ClassifyReason 的关键字（否则分类落"出图失败"）。
        自测断言与实现同步演进：断言用旧版公式长期 FAIL 是断言陈旧，
        应对齐现行设计（v4.4 修正 PISCES 比例 / plot 窗口 3 条遗留断言）。

【迭代时的常规流程】
    1. 明确本次要改的能力。
    2. 定位对应源文件（按上面职责/关键词）。
    3. 修改 → dotnet build -c Release（主工程 + 自测试工程回归）。
    4. 用测试 dwg 跑自测（自测试工程\说明.txt 有全部命令；改代码后先跑
       快速回归三件套：默认单元断言 / --sync / --dc）。
    5. 用新 exe + extframe.lsp + extframe_company.lsp + 公司图框标准库.json 覆盖
       发布程序 v4.17\（改动 LISP 时须 4 处同步：源码工程 / 源码工程 bin Release
       / 发布程序 v4.17 / 自测试工程 bin Release）。
    6. 重要改动建议：全量 --dirc / --dir 端到端验证 + 视觉抽检 PDF。
    7. UI 改动验证（宿主无桌面会话时）：编译 0 错误 + 静态检查
       （字段/事件/布局引用完整性）+ 发布机器人工验收；
       引擎数据流改动靠 --dc / --dirc 断言验证。
    8. 新版本目录：先建版本号递增文件夹（如 v4.17），从上一版复制后升级；
       完成后按用户规范保留"最新 + 两个相近版本"。
