一、版本定位
  【当前正式交付版 = v4.17】本版为"识别速度 + 质量审查 + 输出整洁"优化轮（详见第十二节）。
  v4.16 的"打印发浅"修复完整保留（第九～十一节）。

  以下为历史沿革：
  v4.16 = v4.15 + "打印发浅"根因定稿修复（布局着色打印组码 76 ≥ 3 → 改走 COM 通道）。
  完整证据链见《经验手册》第27章（选纸跳档，已被推翻）/ 第28章（OLE 光栅化）/
  第29章（根因定稿 = 组码 76≥3）。

  v4.15 = v4.14 + **含图片图纸的高清出图**（新增设置项，可实现"光栅图像质量"）。
  起因：用户提出"含图片图纸需要调光栅图像质量（建议 1200/4800），做成设置入口"，
  并给出打印对话框「PDF 选项 → 质量」截图与样图。
  实现：含真光栅图片的图纸改走 **COM（AutoCAD 打印）路径 + 现场生成的高清 pc3**——
  实测 accoreconsole 的 -EXPORT **不认打印质量/设备**（图片被压到 ~26-44dpi），
  而 COM 路径认 pc3 的"光栅图像质量"（实测 28dpi → 166dpi，约 6 倍）。
  完整证据链、pc3 容器格式与踩坑见《经验手册》**第26章**（含 2026-09-16 全量实测修正）。

三、触发条件（2026-09-16 全量实测后收紧，重要）
  只对**同时满足三条**的图纸启用 COM 高清：
    ① 含**真 IMAGE（光栅图像）实体**——OLE 嵌入图片、PDF/DWF/DGN 参考底图**不算**；
    ② 这些 IMAGE 中**没有"外部图文件缺失"**的（path 非空但 findfile 失败）；
    ③ 设置项未关闭（dpi > 0）。
  收紧原因（首轮全量 183 张实测，见《手册》第26章末）：
    · 首轮把"IMAGE + 图片型 OLE + 参考底图"共 35 张送 COM，真含 IMAGE 的仅 8 张；
      24MB 级大图白走 COM，**单张最慢 932s** → 全量 725s 恶化到 2570s ✗；
    · 6 张 H77_"双面胶"的图片路径指向他人桌面（文件缺失），**COM 打印输出空白页** ✗
      （accoreconsole 通道正常——这类图不送 COM 即可）。
  另加**两道安全网**（绝不漏图）：
    ① COM 高清出图失败（含"产出空白页"）→ 自动回退常规通道重试；
    ② COM 兜底也失败 → 再重试常规通道一次。依据：accore 的"未能找到路径中的某个部分"
       是**瞬态**（批量时偶发、隔离复跑即消失，v4.12 时代亦有记录）；实测公司版 40 张里
       4 张"坐垫按摩气袋"曾被它连带失败（隔离复测 10.2s 正常出图）。

九、v4.16 修订（2026-10-07）：PISCES 2A0 图纸"打印发浅" —— 已修（根因在选纸，不在页面设置）
  现象：`测试文件输入\打印问题文件` 下 8 张 PISCES 图纸打印后"文字可读但图形线条浅"。
  参照：用户手动打印记录（该目录 plot.log）= **ISO full bleed 2A0 (1189x1682) 1:1**。
  根因：这批图纸图框 **1692 x 1199mm**，只比 2A0(1682x1189) 大 10mm；原选纸逻辑拿
  "图框+2×边距(20mm)"与纸型**严格**比较，两个方向都超 ⇒ 被顶到 **4A0**，内容随之缩到
  1/1.41。按页缩放查看/打印时，线宽相对纸面宽度细了一半 ⇒ "发浅"；文字因字高远大于线宽
  仍然可读。⚠ 选"贴边(边距=0)"**不能**绕过（1692 仍 > 1682）。
  修复：
   1) 选纸比较加 **3% 容差**（`PageSpec.PaperFitTolerance`）：允许纸型比"图框+2×边距"最多
      小 3%，由既有缩放公式 `s=min((纸长-2M)/窗口长,(纸短-2M)/窗口短)` 把内容缩一点点放下去。
      3% 的来历：该批短边需求 1219mm 对 2A0 短边 1189mm 超出 2.52%（2% 实测不够，会被顶到 4A0）。
      只影响"图框略微超纸"的图纸（即此前出问题的这批），其余图纸选纸结果**逐位不变**。
   2) **修掉一个自 v4.1 起一直失效的设置**：界面「显示线宽」设的是 COM 属性 `PlotLineweights`，
      而 Layout 对象**没有这个属性**（每次抛异常被吞）⇒ 该设置从未生效过。正确属性名是
      **`PlotWithLineweights`**（另有 `ScaleLineweights` = LWDSCALE 缩放开关），已改正。
   3) accore 出图脚本按正确意图写组码 70 的 **0x80 位**（"打印线宽"）。实测：COM 把
      `PlotWithLineweights` 置 true 后 Model 布局组码 70 由 11828→11956（+0x80），而 `LWDISPLAY`
      仍为 0 ⇒ 出图引擎读的是布局标志位，不是该系统变量。
  实测效果（8 张问题图纸，新旧对照）：
      页面      1682x2378mm（4A0） → **1189x1682mm（2A0）**
      内容占纸面长边 ~71% → ~99%
      有效分辨率 296dpi → **396dpi（+33%）**
      转换 8/8 成功，104.4 秒
  回归：`--unit` 34 断言全过；默认断言集 78 全过（新增 7 条覆盖选纸容差）；
        公司版 40 张 40/40 成功 0 失败；8 张源图 MD5 改前改后一致、无 recover/bak 残留。
  已知限制（实测，勿重复投入）：**accoreconsole 的 -EXPORT 不认打印设置** ——
  LWDISPLAY 0/1、组码 70 的 0x80 开/关、组码 146 着色打印 0/1/2 四组对照的 PDF 内容流
  md5 完全相同；这条通道只能靠"选纸/窗口/比例"改变结果。若这批图纸仍偏浅，下一步是把它们
  改走 COM 打印通道并置`PlotWithLineweights=true`（实测能让像素变多）。

       Y1567530 2A0 1.5MB  OLE2FRAME=0  -> 矢量

     与纸型、线宽开关、文件大小都无关（1.5MB 的 Y1567530 就是矢量）。

  4) 未做（需用户决策）：出图前隐藏 OLE2FRAME 让整页走矢量，代价是丢掉嵌入的参考底图。

十三、v4.17 修订二（2026-10-15）：问题图纸出图错位/裁切 —— 已修（根因在 UCS，不在识别）
  【背景】用户三张问题图纸（557 27MY-Y1736904 / Y1736910 / Y1736911，测试文件夹输入\问题图纸-10.14）
  出图 PDF 内容被推到页面一角：墨迹仅 654.4×856.6mm，左边距 12.7、右边距 173.9、
  上边距 318.1、下边距 14.1 —— 左侧 ~18%、底部 ~25% 的图形被裁掉，页面顶部留 318mm 空白。
  同批图纸用 AutoCAD 手工出图正常。

  ── 根因：源图保存过"非世界 UCS"，识别坐标与出图窗口坐标系不一致 ──
  探针实测（_probe_ucs.lsp）：
    WORLDUCS = 0
    UCSORG   = (229.022652, 215.701971, 0)   ← 恰好等于识别出的图框左下角
    UCSXDIR  = (1, 0, 0) / UCSYDIR = (0, 1, 0)   ← 轴向与 WCS 平行，仅原点平移
    VIEWCTR  = (594.509, 420.500)            ← = 1189/2, 841/2 ⇒ 图框在 UCS 下即 (0,0)-(1189,841)
  链路：
    · 图框识别（FrameExtractor/extframe.lsp）从实体 entget 读坐标，得到的是 **WCS** 图框
      (229.022652,215.701971)-(1418.022652,1056.701971)（1189×841，识别本身完全正确）；
    · 出图脚本把这个 WCS 图框直接写成 -EXPORT 的 Window 应答，而 -EXPORT 的窗口
      按 **当前 UCS** 解释 → 实际出图窗口 = WCS 图框 + (229.02, 215.70)；
    · 于是出图窗口整体平移，真实图框 (WCS) 落在窗口左下外侧 → 左/底被裁、右上留大片空白。
  之前怀疑的"图层 0 存在幽灵矩形不打印"是误判：那 187 条 0 层线就是真实图框本体，
  分区出图测得 ink=0 只是因为那个分区在（已错位的）窗口坐标系里恰好没有内容。

  ── 修法：出图前把 UCS 复位为世界坐标系（三处出图窗口注入点全覆盖）──
   1) `PlotSession.BuildScript`（accoreconsole -EXPORT 主通道）：脚本在 FILEDIA/BACKGROUNDPLOT
      之后插入 `(command "_.UCS" "_World")(princ)`，再执行页面设置 entmod 与 -EXPORT。
   2) `CadConverter.TryResetUcsToWorld`（COM 兜底通道）：在 d.Set("ActiveLayout") 之后、
      SetWindowToPlot 之前调用。实现：首选 ActiveUCS 属性同步复位（Origin=(0,0,0)、
      XAxisVector=(1,0,0)、YAxisVector=(0,1,0)，再回写 ActiveUCS），随后 GetVariable("UCSORG")
      校验；失败再 SendCommand "_.UCS _World" 兜底并轮询 3s。任何失败只提示一次、不阻断出图。
   3) `PageSetupPreprocessor`（COM 页面设置预处理副本）：精确模式 SetWindowToPlot 之前调用同一方法。
   为什么"复位"而非"坐标变换"：复位后 WCS==UCS，无论底层用哪一种解释都得到正确窗口；
   对本来就是世界 UCS 的图纸是空操作（零回归）；无需改动 extframe.lsp、FrameCache、自测试断言。

  ── 验证 ──

     **WinForms 的 Dock 布局按 z-order 逆序处理（后 Add 的先占位）** —— 标题先吃满整行 24px，

     （标题 Dock=Left 先 Add、按钮 Dock=Right 后 Add），所以那两个按钮正常。
   修法：交换两行 Add 顺序（标题先 Add）。
   ⚠ 通用陷阱：凡 "Dock=Top 的标题 + Dock=Right 的按钮" 的头部面板，标题必须先 Add。
